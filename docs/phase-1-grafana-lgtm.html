Phase 1 · Observability with OpenTelemetry

A real backend

The debug exporter is replaced by Tempo, Loki and Prometheus. The receiver, the processors and the telemetry script do not change by a single byte. This phase exists to prove that claim and to show what it costs.

01

One block changed

Phase 0 ended with three pipelines that all pointed at stdout. Phase 1 points them at three databases instead. Everything upstream of the arrow is untouched.

This is the seam working as advertised. send-telemetry.sh is copied across verbatim — it still sends the same hand-written OTLP JSON to the same port — and the application, if there were one, would need no rebuild, no restart and no awareness that a storage layer now exists.

Note the exporter names. In Collector 0.149 the component ids otlp and otlphttp were renamed to otlp_grpc and otlp_http. The old spellings still work and still load, but they log a deprecation warning at startup. Most tutorials you will find online use the old names.

02

Two exporters that look the same and are not

OTLP has two transports. Which one you use is decided by the receiving product, not by preference.

Default port43174318
endpoint valuehost:port — no schemea full URL, scheme required

The one that gets everybody

The otlp_http exporter appends the signal path itself. Loki's OTLP base path is /otlp, so the endpoint is http://loki:3100/otlp — not http://loki:3100/otlp/v1/logs. Write the longer one and the Collector cheerfully requests /otlp/v1/logs/v1/logs and drops every record on a 404. You will run exactly this break in section 6.

Queue and retry are not decoration

Two sub-blocks turn the exporter from fire-and-forget into something that survives a backend restart:

  • sending_queue — an in-memory buffer between the pipeline and the network. num_consumers is the export concurrency; queue_size is how many batches may wait. When it fills, new data is dropped and counted, not blocked.
  • retry_on_failure — exponential backoff between initial_interval and max_interval, giving up at max_elapsed_time. A permanent error such as a 404 is never retried; only transient ones are.

In memory is the operative phrase. Kill the Collector with a full queue and that data is gone. Phase 6 puts the queue on disk with the file_storage extension.

03

Your metric name will not survive

OTLP and Prometheus disagree about what a metric is called and what a label is. Prometheus resolves the disagreement by rewriting your data on ingest.

The second surprise is the expensive one. A resource attribute is the join key across all three signals — it is how a trace in Tempo and a log line in Loki and a series in Prometheus are known to belong to the same service. Prometheus drops it by default. Forget the promotion list and service.name is simply not queryable, and no error says so.

Promote deliberately, not generously. Every promoted attribute multiplies into the series count exactly as Phase 0's cardinality arithmetic predicts. service.name, service.namespace, deployment.environment are bounded and worth it. host.name in a cloud autoscaling group is not.

04

Correlation is configured, not stored

Phase 0 stamped a trace_id onto a log record. Nothing in Tempo or Loki does anything with that on its own. The link between them is a Grafana datasource setting.

Loki 3 exposes OTLP log attributes as structured metadata — queryable key-values that are not part of the stream label set and therefore do not create a new stream. That distinction matters: trace_id as a label would be catastrophic cardinality, one stream per request. As structured metadata it is filterable at query time and costs nothing at index time. This is why the derived field uses matcherType: label against the field directly rather than regexing it out of the message body, which is what every pre-OTLP Loki tutorial does.

05

The config

phase-1/otel-collector-config.yaml — exporters and service only; the rest is phase 0 verbatim

exporters:
  otlp_grpc/tempo:              # Tempo speaks OTLP/gRPC natively
    endpoint: tempo:4317       # host:port, no scheme — this is gRPC
    tls:
      insecure: true            # local only; never in production
    sending_queue:
      enabled: true
      num_consumers: 4          # export concurrency
      queue_size: 1000          # batches held in memory when the backend is down
    retry_on_failure:
      enabled: true
      initial_interval: 1s
      max_interval: 10s
      max_elapsed_time: 60s     # after this, the batch is dropped and counted

  otlp_http/loki:                # base path only — the exporter appends /v1/logs
    endpoint: http://loki:3100/otlp
    tls:
      insecure: true

  otlp_http/prometheus:          # needs --web.enable-otlp-receiver on Prometheus
    endpoint: http://prometheus:9090/api/v1/otlp
    tls:
      insecure: true

  debug:                        # kept alongside, so stdout stays a second opinion
    verbosity: basic

service:
  extensions: [health_check]
  pipelines:
    traces:
      receivers:  [otlp]
      processors: [memory_limiter, batch]
      exporters:  [otlp_grpc/tempo, debug]     # fan-out: two exporters, one copy each
    metrics:
      receivers:  [otlp]
      processors: [memory_limiter, batch]
      exporters:  [otlp_http/prometheus, debug]
    logs:
      receivers:  [otlp]
      processors: [memory_limiter, batch]
      exporters:  [otlp_http/loki, debug]

Listing two exporters is fan-out: the pipeline hands each batch to both, independently. A failure in one does not stall the other, which is exactly the property Phase 4 relies on when Grafana and Elastic run side by side.

server:

Tempo 3 changed shape

Nearly every Tempo example online sets ingester: and compactor:. Tempo 3 replaced that pair with a live-store and block-builder architecture, and those keys no longer exist. Paste an old config and you get field ingester not found in type app.Config and the container exits. Tempo also refuses to start with no config file at all — there is no useful default. The same is true of Loki.

phase-1/prometheus/prometheus.yml

global:
  scrape_interval: 15s

# OTLP resource attributes are NOT labels unless promoted here.
# Without this list, service.name is not queryable.
otlp:
  promote_resource_attributes:
    - service.name
    - service.namespace
    - service.version
    - deployment.environment

scrape_configs: []              # nothing is scraped; everything arrives as OTLP

An empty scrape_configs is worth pausing on. This Prometheus pulls nothing. It is a pure OTLP sink, which is a genuinely unusual way to run it and only possible because of --web.enable-otlp-receiver. Phase 3 adds scraping — but on the Collector, not here.

phase-1/grafana/provisioning/datasources/datasources.yaml

# Read once at startup. Restart Grafana after editing this file.
apiVersion: 1

datasources:
  - name: Prometheus
    uid: prometheus            # fixed uid so the other two can reference it
    type: prometheus
    url: http://prometheus:9090

  - name: Loki
    uid: loki
    type: loki
    url: http://loki:3100
    jsonData:
      derivedFields:            # log line -> trace
        - name: trace_id
          matcherType: label      # match structured metadata, not a regex on the body
          matcherRegex: trace_id
          datasourceUid: tempo
          url: "${__value.raw}"
          urlDisplayLabel: View trace

  - name: Tempo
    uid: tempo
    type: tempo
    url: http://tempo:3200
    jsonData:
      tracesToLogsV2:           # span -> logs
        datasourceUid: loki
        spanStartTimeShift: -5m  # widen the window; clocks and batching drift
        spanEndTimeShift: 5m
        filterByTraceID: true
        tags:
          - key: service.name       # OTLP spelling in Tempo...
            value: service_name    # ...Loki spelling in Loki

That last pair of lines is the whole cross-store impedance mismatch in miniature. Tempo keeps the OTLP attribute name with dots; Loki normalised it to underscores on ingest. Grafana needs both spellings told to it explicitly. Expect the same translation work every time two stores meet.

07

Break it on purpose

Predict the outcome before you run each one. Restart the Collector after every edit: docker restart otelcol.

ChangePredictWhat actually happens
docker stop tempo, then resend Traces lost? All three signals fail? Or something else? The script still prints three 200s — the receiver does not know. Logs and metrics land normally. The traces exporter retries with growing backoff for 60 s. docker start tempo inside that window and the trace arrives intact.
Loki endpoint → http://loki:3100/otlp/v1/logs Works, or 404? 404 on /otlp/v1/logs/v1/logs. Marked permanent, so it is not retried — the batch is dropped immediately.
Delete tls.insecure: true from the Tempo exporter Connection refused? Timeout? Clean error? tls: first record does not look like a TLS handshake, repeating from the gRPC layer. The Collector starts fine; the failure is per-connection.

Edit datasources.yaml without restarting Grafana Picked up on next query? No. Provisioning files are read once at startup. docker restart grafana.

08

Answer these before Phase 2

  • 01

    You changed nothing but the exporters block, yet the metric you query in Grafana has a different name than the one you sent. Where did the rename happen, and could the Collector have prevented it?

    Answer

    In Prometheus, on ingest. Prometheus applies its OTLP translation strategy: dots and other illegal characters become underscores, the unit is appended where it is a known one, and a monotonic sum gets _total. The Collector sent orders.created untouched.

    It could be prevented, in two ways, neither free. Prometheus can be told to keep names as-is by changing the translation strategy, at the cost of names that are not valid PromQL identifiers without quoting. Or the Collector can rename the metric itself with metricstransform before export — which means your metric names now depend on which backend you happen to be exporting to, defeating the point of the seam. Living with the translation is usually correct.

  • 02

    otlp_grpc takes endpoint: tempo:4317 and otlp_http takes endpoint: http://loki:3100/otlp. Why does only one of them need a scheme, and why does only one of them need tls.insecure?

    Answer

    The HTTP exporter builds a URL, so the scheme is the transport decision — http:// already means plaintext and tls.insecure is redundant. The gRPC exporter dials a host and port; there is no scheme to carry that information, so security is a separate setting and the default is TLS on. Omit it against a plaintext server and you get the handshake error from break 3.

    Second half of the answer: the HTTP exporter also owns the path. It appends /v1/<signal>, which is why the endpoint is a base path. gRPC has no equivalent because the method name is fixed by the OTLP service definition.

  • 03

    A log record in Loki carries trace_id. A span in Tempo carries the same value. Nothing links them until you do something. What, and where does it live?

    Answer

    Two Grafana datasource settings, both in datasources.yaml and neither in the data. derivedFields on the Loki datasource turns the trace_id field into a link to the Tempo datasource. tracesToLogsV2 on the Tempo datasource turns a selected span into a Loki query filtered by trace id.

    Consequence worth internalising: correlation is a property of the query layer, not the storage layer. Move to Kibana in phase 4 and the stored data is identical, but every correlation link has to be rebuilt in Kibana's own terms. The data model is portable; the experience is not.

  • 04

    Why is trace_id structured metadata in Loki rather than a stream label — and what would happen if it were a label?

    Answer

    Loki indexes stream labels and shards chunks by label set. A unique trace_id per request would create one stream per request: unbounded stream cardinality, an index larger than the logs, and eventually an ingester that will not start. This is the Phase 0 cardinality lesson in Loki's dialect.

    Structured metadata is stored alongside each line and filterable at query time without being part of the index. You pay a scan instead of an index write, which is the correct trade for a field that is high-cardinality but only ever queried for one exact value at a time.

  • 05

    Tempo is down for two minutes. Nothing errors at the application. Where is the data, and at what point is it actually lost?

    Answer

    In the Collector's sending_queue, in memory, in the exporter's process. It is lost at whichever comes first: max_elapsed_time (60 s here, so two minutes loses it), the queue filling to queue_size and rejecting new batches, or the Collector process restarting.

    All three are silent to the sender, which already got its 200 from the receiver. The only place the loss is visible is the Collector's own logs and its otelcol_exporter_send_failed_spans counter. An unmonitored pipeline that drops data is worse than no pipeline — it produces confident, wrong dashboards. Phase 6 fixes the durability with the file_storage extension and the visibility by scraping the Collector itself.

  • 06

    Phase 2 adds a real application. Which of the three signals will change character most, and why is that the reason the app is not optional?

    Answer

    Traces. The two spans here were typed by hand into a shell script; they demonstrate the data model and nothing else. Real traces are generated by instrumented client libraries, which means the shape of the trace is the shape of the code path — and that is the only thing that can tell you which of five services made a request slow.

    It is the reason the app is mandatory rather than a nice demo: MongoDB, RabbitMQ and MinIO emit no spans and never will. Every span in this project's future comes from the mongodb, amqplib and @aws-sdk/client-s3 libraries running inside our own process. Without an application, phases 3 to 6 are a metrics-and-logs exercise.
