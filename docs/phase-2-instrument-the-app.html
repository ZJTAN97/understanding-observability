Phase 2 · Observability with OpenTelemetry

Context across a queue

Two services, one broker between them, and a single trace that spans both. This is where OpenTelemetry stops being plumbing: the value is not that spans exist, it is that a span emitted in one process knows it is a child of a span emitted in another.

Runtime Docker Compose New Java agent · RabbitMQ · MongoDB · MinIO Time ~90 min Ends with seven spans, two services, one trace_id
01

Only the app can produce a trace

MongoDB, RabbitMQ and MinIO expose metrics and write logs. None of them emits a span, and none of them ever will. Every span in this project comes from a client library running inside our own process.

That is not a gap in their feature sets. A trace is a record of one request moving through a system, and the only component that knows a request is one request is the code that issued it. The database sees an insert; the broker sees a publish; neither has any idea they belong to the same POST /orders. The client library does, because it is running inside the call stack that does.

The service graph makes this visible as data. After a few minutes of traffic the servicegraph connector reports an edge order-worker → unknown alongside the real one — those are the worker's CLIENT spans to MongoDB and MinIO, which have no matching SERVER span on the other side because there is nothing on the other side that speaks OTLP.

02

The agent gets in before your code

Auto-instrumentation is not magic and it is not static analysis. In Java it is bytecode rewriting: the agent registers a transformer with the JVM, and every time a class it recognises is loaded, the class that reaches memory is not the class that was on disk.

The hook is premain. The JVM runs it after the core runtime is up and before the application's main method — before Spring exists, before a single one of your classes has been loaded. That ordering is guaranteed by the JVM specification, not by your command line, which means the whole category of “I initialised the SDK too late” bugs cannot happen here.

What can happen is that the flag is simply absent. Then nothing is rewritten, nothing warns you, and the application works perfectly.

Measured, on this app: removing -javaagent from order-api produced zero traces in a sixty-second window against thirty-two in the window before it, while the worker kept emitting eighty-one. Not one line in the API's log matched error. The service accepted orders, published them to RabbitMQ, and returned 202 the whole time.

The clearest tell is in the logs themselves, and it is easy to miss:

order-api, with and without the agent

INFO [84edec4df388cc69ec8d62bd7866d215,b2394fce0dab74b1] --- ApiController : published orders.created
INFO [,] --- ApiController : published orders.created

The second line is not missing a field. The field is there, holding the empty string, because the log pattern reads %mdc{trace_id} and the MDC key was never populated — there was no instrumentation to populate it. A bare [,] in production logs means the agent is not attached.

Three ways to instrument Spring Boot, and they disagree

The agent is one of three paths, and the two organisations involved recommend different ones. This is worth knowing before someone on your team asks why you did not do it their way.

PathOwnerWiringCoverage
OTel Java agent ← this phaseOpenTelemetry-javaagent: flag~130 libraries, including non-Spring ones
OTel Spring Boot starterOpenTelemetryone dependencynarrower; works with GraalVM native image
Micrometer + OTel bridgeSpringmicrometer-tracing-bridge-otel and management.* propertiesonly what Spring itself instruments

OpenTelemetry's own documentation treats the agent as the default and the starter as what you reach for when an agent cannot run. Spring recommends neither: all Spring projects instrument themselves through the Micrometer Observation API, so their position is that you should bridge that to OTLP rather than rewrite bytecode underneath it. Their objections to the agent are specific — it pulls in alpha-versioned jars, it is incompatible with GraalVM native image and the AOT cache, and version mismatches between agent and library are hard to diagnose. In Spring Boot 4.0 their answer ships as org.springframework.boot:spring-boot-starter-opentelemetry, a name one word away from OpenTelemetry's own.

The agent is used here for three reasons. It reads the same OTEL_* environment variables as every other SDK in this curriculum, so there is one configuration vocabulary to learn rather than two. It instruments libraries Spring knows nothing about. And it is the honest analogue of the loading-order lesson that every other language has to teach the hard way.

Two concrete gaps in the Micrometer path are worth carrying with you even if you never use it. It does not instrument the AWS SDK at all — a receipt written to S3 produces no span. And Spring AMQP ships with observationEnabled = false, so traceparent is never injected into a message until you set that flag explicitly on both the RabbitTemplate and the listener container factory. Miss it and you get two perfectly healthy services and no trace connecting them.

Pin the agent

Every tutorial links releases/latest/download/opentelemetry-javaagent.jar. That URL means the instrumentation attached to your application can change version between two builds of the same commit, with no diff to show for it. The Dockerfile here pins v2.31.1 in an ARG.

03

Carrying context through RabbitMQ

Inside one process, the active span travels in async-local storage: any function called from inside a span sees it, including across await. Between two processes there is no shared memory, so context has to be serialised, put in the message, and read back out.

The serialised form is one header, defined by W3C Trace Context and identical whether the transport is HTTP, gRPC or AMQP:

traceparent

00-4ba57203c9c4e19dee4dcad86fed3a90-a1146f338e795901-01
│  │                                │                │
│  │                                │                └─ flags: 01 = sampled
│  │                                └────────────────── parent span id (8 bytes)
│  └─────────────────────────────────────────────────── trace id (16 bytes)
└────────────────────────────────────────────────────── version

Two things follow, and both are load-bearing.

The consumer span must be created inside the delivery callback. The instrumentation makes the extracted context active for the duration of that callback and no longer. Push the message onto a queue and process it from a timer and the context is gone — not corrupted, just absent. Section 07 runs exactly that.

Parent-child is the wrong relationship for a batch. A span has one parent. A consumer that handles fifty messages in one batch has fifty upstream traces, so the correct model is a single CONSUMER span with fifty span links — a non-hierarchical reference that says “caused by” without claiming a parent. Links also carry no sampling decision, which is the point: fifty parents cannot all decide whether the batch is sampled.

04

Span kinds, and what they are for

Kind is not decoration. It is the field that lets a backend pair two spans from two processes into one edge of a service graph, and it is the field that decides whether a span counts as a request the service served or a request it made.

KindIn this tracePairs withWhat it means
SERVERPOST /ordersa remote CLIENTThis process handled an inbound request. Latency here is what a caller experienced.
CLIENTinsert shop.orders, PUTa remote SERVERThis process made an outbound call and waited. Includes network time.
PRODUCERorders publisha CONSUMER, laterHanded a message to a broker. Ends when the broker accepts it, not when anyone processes it.
CONSUMERorders.created processan earlier PRODUCERPicked a message up. May start seconds or hours after its parent ended.
INTERNALnone in this tracenothingWork inside one process. The default, and the right choice for a custom span that is not a call.

The PRODUCER/CONSUMER pair is the one that behaves unlike the others. A CLIENT span strictly contains its SERVER span in time; a PRODUCER span does not contain its CONSUMER span, and in a backed-up queue it can finish long before the consumer starts. A trace waterfall with a child that begins after its parent has ended is not a bug — it is what asynchronous work looks like, and reading it correctly is the skill.

The servicegraph connector uses kind to decide what an edge is. It labels the RabbitMQ hop connection_type="messaging_system" precisely because it paired a PRODUCER with a CONSUMER rather than a CLIENT with a SERVER.

Where the extra spans come from

The trace has seven spans, not the six the pipeline suggests, and the extra one is a second CONSUMER span. Two of the agent's modules instrument the same message: rabbitmq-2.7 wraps the raw AMQP client and emits orders process, 0.09 ms and childless; spring-rabbit-1.0 wraps the @RabbitListener and emits orders.created process, 10.45 ms and parent of everything the worker does.

The instinct is to switch one off. Doing so — OTEL_INSTRUMENTATION_RABBITMQ_ENABLED=false — was measured here, and it destroys the trace: the PRODUCER span disappears and the worker's spans become separate roots, because traceparent injection lives in the low-level module and not in the Spring one. The instrumentation that wraps your code is not necessarily the instrumentation that carries your context. Nested spans from two layers are normal, and deduplicating them by guesswork is how you lose a trace.

There is no instrumentation file. That is the headline. The entire OpenTelemetry configuration for both services lives in a command line and a block of environment variables, and not one class in shop.orders imports a tracer, a span, a context or a propagator.

app/src/main/java/shop/orders/OrderListener.java — the consumer, and the one rule about it

// The agent extracts traceparent from the message headers and makes the
// CONSUMER span current for the duration of THIS method. Everything called
// from inside inherits it. Everything handed to another thread does not.
@RabbitListener(queues = "${app.queue}")
void onOrder(Order order) {
  if (cfg.detachContext()) { pending.add(order); return; }   // break #2
  handle(order);
}

private void handle(Order order) {
  long started = System.nanoTime();
  String status = "ok";
  try {
    // three CLIENT spans, in this order, all children of the CONSUMER span
    mongo.getCollection("orders").insertOne(doc);
    minio.putObject(PutObjectArgs.builder().bucket(...).object(key)....build());
    if (order.qty() > 90) throw new IllegalStateException("exceeds per-order limit");
    mongo.getCollection("orders").updateOne(...);
    log.info("order receipted order.id={}", order.id());
  } catch (Exception e) {
    status = "error";
    // The agent marks a span ERROR only when the method it instrumented throws.
    // This exception is caught here, so the CONSUMER span would end UNSET and the
    // failure would be invisible to {status=error} in Tempo. Two lines fix it.
    Span span = Span.current();
    span.recordException(e);
    span.setStatus(StatusCode.ERROR, e.getMessage());
    log.error("order processing failed order.id={}", order.id(), e);
  } finally {
    telemetry.orderProcessing.record((System.nanoTime() - started) / 1e9,
        Attributes.of(STATUS, status));
  }
}

Note what is not here. No Tracer, no SpanBuilder, no Scope, no try-with-resources around a context. The three CLIENT spans exist because the Mongo driver and OkHttp were rewritten at class load, and they are children of the CONSUMER span because the agent left that span current on this thread.

The catch block is the exception to that, and it is worth understanding why it has to be. An agent can only mark a span as failed when the method it instrumented throws. Here the exception is caught inside handle, so onOrder returns normally and, as far as spring-rabbit can tell, the delivery succeeded. Before those two lines were added this application logged twenty-nine processing failures in five minutes and Tempo held zero spans with an error status — the failure existed in the log line and in the status="error" metric label, and nowhere a trace search could reach it.

Span.current() returns the span the agent made current; recordException attaches the type, message and stack trace as a span event; setStatus is what {status=error} actually queries. It also propagates outwards: the servicegraph connector starts reporting a failed order-api → order-worker edge, which was flat at zero before.

app/src/main/java/shop/orders/Telemetry.java — the only OTel import in the app

// API only, no SDK. This exists because two metrics are hand-written, and
// hand-written telemetry needs types to write against. Tracing needs nothing:
// delete this file and every span in the waterfall still appears.
private final Meter meter = GlobalOpenTelemetry.get()
    .getMeterProvider().meterBuilder("shop").setInstrumentationVersion("0.1.0").build();

// Counter: how many. `channel` has three values forever. `order.id` here
// would be one time series per order — the phase 0 arithmetic, for real.
final LongCounter ordersCreated = meter.counterBuilder("orders.created")
    .setDescription("Orders accepted by the API")
    .setUnit("{order}")
    .build();

// Histogram: how long. Label set again bounded — status is ok|error.
final DoubleHistogram orderProcessing = meter.histogramBuilder("order.processing.duration")
    .setDescription("Time from consume to final Mongo update")
    .setUnit("s")
    .build();

GlobalOpenTelemetry.get() is the seam between the two halves. With the agent attached it returns the real SDK the agent installed during premain. Without it, it returns a no-op: Telemetry still constructs, ordersCreated.add(1, ...) still accepts the call, and the number goes nowhere. Nothing throws. During break #1 the series orders_created_total did not merely stop increasing — it stopped existing.

Auto-instrumentation cannot see a caught exception

This generalises well beyond RabbitMQ. Any try/catch that swallows a failure inside your own method is invisible to every agent, in every language — instrumentation watches boundaries between your code and a library, and a caught exception never crosses one. If your service degrades gracefully by design, it degrades silently in your traces by default. The alternative fix is to let the exception escape the listener, but on a `@RabbitListener` that means the broker requeues the message; without spring.rabbitmq.listener.simple.default-requeue-rejected=false or a dead-letter queue you have traded a silent failure for a poison-message loop.

There is no shutdown hook here

The Node version of this app had to call sdk.shutdown() on SIGTERM or lose the last batch of every signal on every deploy. The agent registers its own JVM shutdown hook and flushes for you. One fewer thing to get wrong, and one fewer thing you will remember to check when telemetry goes missing at exactly the moments you care about.

The Collector gains exactly one new component. Nothing in the exporters changed.

phase-2/otel-collector-config.yaml — the new block

# A connector is an exporter on one pipeline and a receiver on another. This
# one consumes traces and emits request/duration metrics per caller-callee
# edge, which is what Grafana's service map is drawn from. No app change.
connectors:
  servicegraph:
    latency_histogram_buckets: [0.1s, 0.25s, 0.5s, 1s, 2s, 5s]
    store:
      # How long an unpaired client/producer span waits for its server/consumer
      # half. The agent's BatchSpanProcessor holds spans for 5 s, so the two
      # sides of one edge routinely arrive seconds apart. The 2 s default silently
      # expires every pair and the service graph stays empty.
      ttl: 30s
      max_items: 10000

service:
  pipelines:
    traces:
      exporters:  [otlp_grpc/tempo, servicegraph]   # fan-out: storage + connector
    metrics:
      receivers:  [otlp, servicegraph]              # app metrics + derived edges
      exporters:  [otlp_http/prometheus]
This cost an hour to find

With the documented default ttl: 2s, the connector starts cleanly, logs nothing, and produces no metrics at all. The client half of each edge expires from its store before the server half arrives, because the agent batches spans for five seconds before exporting. A component that is configured, wired into a pipeline, running, and silently emitting nothing is the phase 0 lesson in a new costume.

07

Break it on purpose

All three of these produce a working application. None of them logs an error. That is what makes them worth doing deliberately once, in a system you understand, rather than accidentally at three in the morning in one you do not.

ChangePredictObserved
remove -javaagent:/otel/opentelemetry-javaagent.jar from order-api No spans from the api. Everything else fine. Worse than predicted. 0 api traces in a 60 s window against 32 in the window before and 81 worker traces still flowing. Zero log lines matching error. The api's log lines show [,] where the ids were. orders_created_total stops existing, not merely incrementing. And the worker's traces become roots at orders.created process — one uninstrumented service breaks the trace for every service downstream of it.
APP_DETACH_CONTEXT: "true" on order-worker — messages parked on a BlockingQueue and drained by a thread started at boot Worker spans become orphan roots. Confirmed, and uniformly. Both CONSUMER spans still join the trace, because extraction happens at delivery — and then the trace stops dead, with no children. Everything the worker actually does detaches into separate roots: over one 60 s window, 25 PUT, 25 insert shop.orders and 23 update shop.orders. Log lines from the detached-drain thread lose trace_id.
OTEL_SERVICE_NAME: order-api on order-worker The service graph collapses. A self-edge order-api → order-api messaging_system appears at 0.900/s while the real order-api → order-worker edge decays to 0.000/s. basic.ack, a worker-only span, starts reporting order-api. On the raw counter the dead edge keeps its last value and sits there looking healthy — this is why you alert on rate(), never on a counter. Every individual trace stays structurally perfect.

Every detached call became its own root. That uniformity is a Java-specific mercy, and it is worth knowing that it is not universal. The Node build of this same application produced a stranger result under the identical bug: S3.PutObject became 29 orphan roots while insert orders returned zero traces and vanished entirely, because instrumentation-mongodb deliberately refuses to create a span when there is no active parent — a defensible choice to avoid flooding a backend with one root per background query — while instrumentation-aws-sdk makes the opposite choice.

The consequence to carry forward: “the spans are missing” and “the spans are orphaned” can be the same underlying bug, and which symptom you see is a property of the library, not of the mistake.

Why this break is easy to believe you are safe from

The agent propagates context across Executor and ExecutorService implementations it recognises, which covers most thread pools you would reach for — @Async, a ThreadPoolTaskExecutor, a CompletableFuture chain. It cannot follow a hand-rolled producer/consumer handoff over a BlockingQueue drained by a thread you started yourself, because there is no call to intercept. The rule is not “avoid threads”; it is that context follows a call, and a queue is not a call.

Restoring

Each break is one line in docker-compose.yaml, and docker compose up -d order-api order-worker applies it. The service-graph counters are cumulative and survive the fix, so after break 3 either wait for rate() to settle or run docker compose down -v && docker compose up -d.

Answer these before Phase 3

  • 01

    Your worker's spans are all orphan roots. Someone suggests the fix is to read traceparent off the message yourself and pass the trace id into the child spans. Why is that not a fix?

    Answer

    Because a trace id alone does not make a parent. A span needs a parent span id and the sampling decision from the flags, and both live in the propagated context, not in a bare id. Copying the trace id onto detached spans produces a trace whose spans all claim to be roots of the same trace — a waterfall with eight top-level bars and no structure.

    The real fix is to restore the active context around the work: keep the processing inside the listener method, or capture Context.current() at delivery and wrap the later work in try (Scope s = captured.makeCurrent()). The second is what a genuine batch consumer does, and at that point you should also be attaching span links rather than pretending to a single parent.

  • 02

    The PRODUCER span lasts 0.17 ms and the CONSUMER span starts 4 ms after it ended. Which of the two tells you the queue is backing up, and what does the other one measure?

    Answer

    Neither, on its own. The PRODUCER span measures only the time to hand the message to the broker — it stays fast while a queue grows to a million messages. The CONSUMER span measures processing, which also stays fast under a backlog.

    The backlog lives in the gap between them, and no single span records a gap. You get at it two ways: derive it from the trace (consumer start minus producer end, which is what an exemplar-linked latency panel does), or read it directly from RabbitMQ's own messages_ready metric. That is the honest reason phase 3 exists — traces tell you about work that happened, and a queue backlog is work that has not happened yet.

  • 03

    You turn off the Mongo statement sanitiser (otel.instrumentation.mongo.statement-sanitizer.enabled=false) so spans carry the real query document. Name two distinct kinds of damage that does in production, and say why one of them is worse in a trace store than in a log store.

    Answer

    Disclosure. The query document goes onto the span as an attribute, so email addresses, tokens and anything else in a filter are now in your telemetry backend, replicated, backed up, and readable by everyone with dashboard access — a population much larger than those with database access.

    Volume and cardinality. Every distinct query document is a distinct attribute value. In a trace store that mostly costs bytes, since traces are not indexed by arbitrary attribute. But anything that derives metrics from spans — spanmetrics, or an OTTL rule promoting an attribute to a label — converts those unique values straight into unique time series. That is the worse path: the log store charges you for storage, the metric store charges you forever, per series, per scrape interval.

  • 04

    One jar runs as both services and the only telemetry difference is OTEL_SERVICE_NAME. What breaks if you set both to the same value — and specifically, is the trace still correct?

    Answer

    The trace is fine. Parent-child linkage is carried by span ids and does not consult service.name at all; the waterfall still shows eight spans in the right order.

    What breaks is everything that aggregates by service. The service graph gains a self-edge and loses the real one. “Which service is slow” becomes unanswerable. Every RED-metric panel sums two workloads with different behaviour into one series. Loki's service_name stream label stops separating the two processes, and a worker-only span such as basic.ack files itself under the API. The failure is entirely at the aggregation layer, which is why it is so easy to ship: every individual trace looks perfect.

  • 05

    The servicegraph connector produced nothing for an hour with a 2 s store TTL. Explain the failure in terms of where the two halves of an edge come from, and say what the equivalent failure will look like in phase 6.

    Answer

    An edge needs a client-side span and a server-side span that reference each other, and they arrive from two different processes on two different batching schedules. The agent's BatchSpanProcessor holds spans for five seconds, so the halves routinely arrive several seconds apart. The connector holds an unpaired half for ttl and then discards it: with ttl: 2s every pair expired unmatched and the connector emitted nothing, silently and without error.

    Phase 6 has the same shape at cluster scale. Tail sampling needs all spans of a trace in one Collector instance before it can decide, so it buffers by trace id for a decision window. Spread those spans across replicas behind a round-robin load balancer and each replica sees a fragment, decides on partial information, and you get incomplete traces. The fix is the same idea as a longer TTL: guarantee the pieces meet, via a loadbalancing exporter keyed on trace id.

  • 06

    Everything in this phase pushes OTLP. Every metric in phase 3 will be pulled by the Collector from an endpoint that has never heard of OpenTelemetry. Which properties of the telemetry you have been taking for granted stop being automatic?

    Answer

    Resource attributes. A scraped Prometheus endpoint has no resource. There is no service.name, no service.version, no deployment.environment unless the Collector attaches them — which is what resourcedetection and attributes processors are for, and why phase 3 spends time on them.

    Semantic conventions. MongoDB names its metrics whatever MongoDB names them. Nothing lines up with the OTel conventions your app follows, so the join keys that make correlation work have to be manufactured with OTTL.

    Trace correlation. There is none, ever. A scraped metric has no trace_id, so the only join available is the resource attributes plus the timestamp. Correlating a Mongo latency spike with a slow trace is a manual act of judgement, not a click — and knowing that in advance is the difference between designing labels that make it possible and labels that do not.

  • 07

    Your trace has two CONSUMER spans for one message: a 0.09 ms childless one from rabbitmq-2.7 and a 10.45 ms one from spring-rabbit-1.0 that parents all the real work. A colleague proposes disabling the useless-looking short one. What happens, and what is the general rule?

    Answer

    The trace is destroyed. Setting OTEL_INSTRUMENTATION_RABBITMQ_ENABLED=false also removes the PRODUCER span on the API side, and the worker's spans become separate roots — because traceparent injection and extraction live in the low-level AMQP module, not in the Spring one. The short span is not the propagation; it is the evidence that the module doing the propagation is loaded.

    The general rule: with an agent, a single logical operation is often covered by two modules at different layers, and the one that looks redundant in a waterfall may be the one carrying context, injecting headers, or setting the span kind that the service graph pairs on. Read the instrumentation scope before you disable anything, and change one module at a time with a trace to check against. Suppressing duplicate spans is a real need — but the correct tool is the module's own suppression config, not switching off a layer wholesale.

  • 08

    Your worker logs order processing failed twenty-nine times in five minutes. A {status=error} search in Tempo returns nothing, and the traces for those orders look completely healthy. The agent is attached and every other span is present. What is happening?

    Answer

    The exception is being caught inside your own method. The agent wrapped @RabbitListener, not your handle(), and it decides a span's status from whether the method it instrumented threw. Your listener returned normally, so the delivery is recorded as a success. Nothing is broken and nothing will warn you — the graceful degradation you deliberately wrote is doing exactly what it was told, in the telemetry as well as in the code.

    Two lines in the catch block fix it: Span.current().recordException(e) attaches type, message and stack trace as a span event, and setStatus(StatusCode.ERROR, ...) is what {status=error} actually matches on. The sibling CLIENT spans should stay UNSET — the Mongo insert and the object write genuinely succeeded, and marking them failed would send the next person debugging this to the wrong system.

    The tempting alternative is to rethrow and let the listener fail. That does produce an error span, and on a @RabbitListener it also makes the broker requeue the message; without default-requeue-rejected=false or a dead-letter queue you have replaced a silent failure with an infinite poison-message loop. Generalise the lesson rather than the fix: an agent sees boundaries between your code and libraries, and a caught exception never crosses one.

Phase 3 promotes the three toy containers to their real topologies — a MongoDB replica set, a RabbitMQ cluster with quorum queues, a MinIO erasure set — and then observes them. The Collector stops being purely a receiver and becomes a scraper: prometheus, mongodb and rabbitmq receivers pulling from endpoints, fluentforward taking container logs, and OTTL dropping the per-collection and per-bucket series that would otherwise multiply without limit.
