Phase 3 · Observability with OpenTelemetry

Infrastructure signals

Three real systems that will never speak OTLP, promoted to their real topologies and then observed — by a Collector that stops being a pipe and becomes a scraper, a log shipper and a translator.

01

The phase the project exists for

Phase 2 traced the application's calls to MongoDB, RabbitMQ and MinIO. It never observed the three systems at all. This is where that changes, and where the Collector's job changes with it.

Two things happen at once. The infrastructure is promoted from one container each to the topology it would actually run in — a three-node replica set, a three-node broker cluster with a quorum queue, a four-node erasure set. And the Collector grows four new receivers, because none of those systems has ever heard of OTLP and none of them ever will.

That second sentence is premise 2 of this curriculum, and it is worth being precise about what follows from it. There is no agent to attach, no SDK to import, no traceparent to propagate. There are no traces at all from any of these three systems — every span you have seen touching them was emitted by a client library inside the demo app. What they offer is a metrics endpoint in someone else's format and a stream of log lines, and the Collector's entire job in this phase is to go and get them.

02

What you lose when you scrape

A pushed OTLP metric arrives wrapped in a resource: who produced it, what version, which environment. A scraped Prometheus endpoint has no such envelope. It has a URL.

The prometheus receiver does what it can: it synthesises a resource from the scrape config, mapping job to service.name and instance to service.instance.id. That is generous, and it is also the source of the first real problem. RabbitMQ is scraped by two jobs, because per-queue metrics live on a different path than the aggregated ones. MinIO is scraped by two jobs, because cluster-wide facts are identical from every node and node facts are not. Left alone, one system becomes two services.

The mongodb receiver is the odd one out and shows the same problem from the other side. It does not scrape a URL, so there is no job to borrow a name from; it reports server.address and nothing else. Left alone, Prometheus's OTLP receiver invents a UUID for instance, and that UUID is different after every Collector restart.

otel-collector-config.yaml — processors

transform/normalise-infra:
  error_mode: ignore
  metric_statements:
    - set(resource.attributes["service.name"], "rabbitmq")
        where IsMatch(resource.attributes["service.name"], "^rabbitmq")
    - set(resource.attributes["service.name"], "minio")
        where IsMatch(resource.attributes["service.name"], "^minio")
    - set(resource.attributes["service.name"], "mongodb")
        where resource.attributes["service.name"] == "mongodb-exporter"
    # the mongodb receiver identifies itself by host and port only
    - set(resource.attributes["service.name"], "mongodb")
        where resource.attributes["service.name"] == nil
            and resource.attributes["server.address"] != nil
    - set(resource.attributes["service.instance.id"], resource.attributes["server.address"])
        where resource.attributes["service.instance.id"] == nil
            and resource.attributes["server.address"] != nil
Collector 0.149 · OTTL context prefixes

In log_statements, a bare attributes["x"] no longer parses. The error is explicit and tells you the fix: missing context name for path "attributes[fluent.tag]", possibly valid options are: "resource.attributes[...]", "log.attributes[...]". Every path needs its context. metric_statements using only resource.attributes are unaffected, which is why half a config can be correct and the other half fatal.

Three other things stop being automatic the moment you pull instead of push, and it is worth naming them now because two of them cannot be fixed:

  • Semantic conventions. MongoDB names its metrics whatever MongoDB names them. mongodb_ss_wt_cache_bytes_currently_in_the_cache is a field path out of serverStatus, mechanically translated. Nothing lines up with the conventions the app follows.
  • Trace correlation. There is none, ever. A scraped metric has no trace_id. The only join available is resource attributes plus a timestamp, and that is a judgement call, not a click.
  • Delivery semantics. A push tells you when it failed. A scrape that returns 401 fails silently on a 15-second loop forever — which is exactly what MinIO does without MINIO_PROMETHEUS_AUTH_TYPE=public.
03

A purpose-built receiver, and why it is not enough

The Collector ships a mongodb receiver that speaks the wire protocol directly, runs serverStatus and dbStats itself, and emits clean OTel-convention metric names. It is the obviously correct choice, and it cannot answer either of the two questions a replica set exists to raise.

mongodb receiverPercona mongodb_exporter
readsserverStatus, dbStatsserverStatus, replSetGetStatus, getDiagnosticData, oplog
namesmongodb.document.operation.countmongodb_ss_* — the serverStatus field path, verbatim
resourceone, for the whole set; no portone, the exporter process
replication lagnot availablemongodb_mongod_replset_member_replication_lag
oplog windownot availableoplog_head_timestamp - oplog_tail_timestamp
electionsnot availablemongodb_rs_term, ..._electionCandidateMetrics_*
series produced~906446 before filtering

That is the trade, stated plainly. A purpose-built receiver gives you a curated, well-named, small metric set — and a curated set is a set someone else finished curating. When the thing you need is outside it, there is no flag to turn it on.

An exporter gives you everything, in the source system's own vocabulary, at the source system's own cardinality. --collect-all --compatible-mode is 6446 series, in two parallel naming schemes, of which perhaps forty are ever looked at.

Running both is not indecision. It is the honest cost, and stating it is more useful than pretending either one is sufficient.

The flag that makes it report zero

--mongodb.direct-connect defaults to true, and a direct connection is invalid with a multi-host URI. Give the exporter a replica-set seed list and the only symptom is mongodb_up 0 and one line in its own log. --no-mongodb.direct-connect is the fix. Nothing in the metric output hints at the cause; you have to go and read the exporter's stderr.

04

Three ways to move a log line

The application's logs arrive by OTLP because the Java agent mirrors Logback into the pipeline. Nothing else in this compose file has an agent, and the two remaining mechanisms are not interchangeable.

The two mechanisms produce visibly different records from the same daemon. mongo1 is tailed as a file and parsed; mongo3 is shipped as a stream and is not:

# file_log receiver + json_parser
instance: mongo1:27017
  body   : Successfully authenticated
  labels : s=I  severity_number=9  severity_text=I  detected_level=I
           c=ACCESS  ctx=conn370  id=5286306  log_file_name=mongod.log
           attr_user=otel  attr_db=admin  attr_mechanism=SCRAM-SHA-256
           attr_metrics_conversation_duration_micros=2623
           attr_metrics_conversation_duration_summary_0_step=1   ... 20 more

# fluentforward receiver, no parsing
instance: mongo3
  body   : {"t":{"$date":"2026-09-04T10:23:29.048+00:00"},"s":"I","c":"NETWORK",...}
  labels : fluent_tag=mongo3  log_iostream=stdout  detected_level=unknown

The parsed one is queryable by severity, by component, by the operation's own fields. It is also expensive in a way that is easy to miss: mongod's attr object is an open set, and every key in it became a piece of structured metadata in Loki. The unparsed one is one string and two labels. Neither is right. The choice is which cost you want, and the honest default is to parse only the fields you will query.

The Collector image runs as an unprivileged user. mongod.log is mode 0600 owned by the mongodb user, and a fresh named volume for file_storage is owned by root. Both fail, and the second one is fatal at startup: storage client: open /var/lib/otelcol/receiver_filelog_mongodb: permission denied. This compose file sets user: "0:0" on the Collector. That is not a shortcut — in phase 5 the DaemonSet Collector runs as root for exactly the same reason, to read /var/log/pods. Every log-collecting agent in production has this property, and it is worth knowing that is what you are deploying.

05

Cardinality, dropped at the pipe

Phase 0 did the arithmetic on paper. Here it is with real numbers: 13 061 active series before filtering, 4 810 after, from nine OTTL rules.

None of what is dropped is broken or wrong. It is all real telemetry, produced by well-behaved software, and it costs exactly as much to store as the telemetry anyone actually looks at.

otel-collector-config.yaml — processors

filter/cardinality:
  error_mode: ignore
  metrics:
    metric:
      # Go runtime of every exporter and MinIO node: 44 + 35x4 series
      - 'IsMatch(name, "^(go_|promhttp_|process_)")'
      # Erlang VM internals x 3 brokers: 4200 series
      - 'IsMatch(name, "^erlang_vm_(allocators|msacc|dist|atom|ets_tables)")'
      # one series per MongoDB command name, issued or not: 862
      - 'IsMatch(name, "^mongodb_ss_metrics_commands_")'
      # WiredTiger internals: 1169 series, three of them on a dashboard
      - 'IsMatch(name, "^mongodb_ss_wt_") and not IsMatch(name,
           "^mongodb_ss_wt_cache_(bytes_currently_in_the_cache|tracked_dirty_bytes_in_the_cache|maximum_bytes_configured)$")'
      # 18 metrics x every collection, system collections included: 450
      - 'IsMatch(name, "^mongodb_top_")'
      # WiredTiger internals of two INTERNAL collections: 324 + 631
      - 'IsMatch(name, "^mongodb_oplog_stats_")'
      - 'IsMatch(name, "_collection_stats_")'
      # host CPU/memory/disk out of /proc: hostmetrics' job, not Mongo's
      - 'IsMatch(name, "^mongodb_sys_")'
      # per-drive, per-storage-API latency: 7 APIs x 4 nodes
      - 'IsMatch(name, "^minio_node_drive_latency_us$")'

A filter processor is the third-best control, and it is worth knowing the two that beat it, because both are used here:

  • Not asking. prometheus.return_per_object_metrics = false keeps RabbitMQ's /metrics at constant cardinality however many queues exist. Per-queue numbers come from /metrics/detailed with exactly three families named in the scrape config. Naming families is the cardinality decision, made before a byte moves.
  • Not scraping. MinIO's /minio/v2/metrics/bucket is never fetched. Bucket count is user input; it does not belong in a metric label at all.

And the Collector will tell you whether a rule does anything, which matters because a rule that matches nothing looks exactly like a rule that works:

$ curl -s localhost:8888/metrics | grep -E 'filtered|accepted_metric_points'
otelcol_processor_filter_datapoints_filtered_total{filter="filter/cardinality"}  58297
otelcol_receiver_accepted_metric_points_total{receiver="prometheus"}             89022
otelcol_receiver_accepted_metric_points_total{receiver="mongodb"}                  340

07

Break it on purpose

The breaks in phases 0 to 2 were configuration mistakes. These are failures — the events the dashboards exist for. Predict each one before running it; the interesting part is usually not the metric you expected to move.

Do thisPredictObserved
docker kill mongo1 an election, a new primary, lag on the returning node mongodb_rs_term 1 → 2 within 45 s; mongo3 becomes PRIMARY; mongo1's series changes member_state to (not reachable/healthy) with value 8. The worker logs 26 driver errors over ~10 s and recovers with no restart. docker start mongo1 and it is re-elected primary in 40 s — it has priority: 2.
stop order-worker, keep publishing backlog climbs, consumers → 0, memory alarm eventually messages_ready 0 → 98 in two minutes, consumers 1 → 0, deliver rate to 0 while publish holds at 0.90/s. No memory alarm — 98 messages is 12 KB against a 256 MB watermark. On restart the deliver rate goes to 1.51/s against a 0.90/s publish rate: that gap is the catch-up, and it is the number to alert on.
docker kill minio4 drives-offline moves, cluster stays readable, healing on return online 4 → 3, offline 0 → 1, erasure_set_status stays 1. Zero application errors — write quorum is 3 of 4. On restart, minio_heal_objects_heal_total ticks up and settles. For a few scrape intervals the surviving nodes disagree about nodes_online (one says 4, two say 3): cluster state is gossiped.
APP_HIGH_CARDINALITY_LABEL: "true" series count climbs without bound orders_created_total 2 → 107 series in three minutes, and third in /api/v1/status/tsdb's ranking — above every metric of all three infrastructure systems except Erlang's allocator table.

The one worth sitting with

Killing the primary does what you expect to the graphs. What it also does is change the identity of series you did not write. The Percona exporter puts the member's state in a label, so a state change does not move a series — it retires one and starts another:

$ curl -sG localhost:9090/api/v1/query \
    --data-urlencode 'query=count_over_time(mongodb_rs_members_state[10m])'

mongo1:27017 PRIMARY                    samples: 19
mongo2:27017 SECONDARY                  samples: 23
mongo3:27017 SECONDARY                  samples: 19
mongo1:27017 (not reachable/healthy)    samples: 4
mongo3:27017 PRIMARY                    samples: 4

Three members, five series, one election. And rs_state is a label on every mongodb_ss_* series too, so a failover briefly forks 4 462 of them.

This is the phase 0 cardinality lesson arriving from a direction nobody plans for. It is not your label. It is on data you only scraped, in a naming scheme someone else chose, and it churns hardest at exactly the moment you are querying it. It also breaks graphs in a specific way: a panel plotting mongodb_rs_members_state shows a line that ends and a different line that begins, rather than one line that changed value. Anything using rate() or increase() across the transition sees a counter reset.

You cannot fix it in the exporter. You can drop the label with a transform statement and keep the numeric value, which is what the state metric was for; or you can accept it and know why the graph looks like that. Deciding which is a real design choice, and it is the same choice phase 6 makes at scale.

Why the fourth break has no pipeline fix

Every other cardinality problem in this phase was solved with five lines of OTTL. order.id on a counter cannot be: the label is on a metric you want, with a value you cannot enumerate, and dropping the label collapses the series you were trying to keep. At one order per second that is 86 400 new series a day, none of them queried twice. The fix is at the keyboard. order.id belongs on a span, where it costs one attribute on one trace — and it is already there.

08

Answer these before Phase 4

Six questions. Write the answer down before opening the disclosure.

  • 01

    You add a fourth RabbitMQ node. Nothing appears in Grafana. The Collector logs no error, the node is healthy, and rabbitmq-diagnostics cluster_status lists it. Where is the bug, and what does that tell you about the prometheus receiver in general?

    Answer

    The scrape config has three static targets, and a fourth node is not one of them. static_configs is exactly as static as it sounds; the Collector never discovers anything it was not told about, and a target that does not exist produces no error because there is nothing to fail.

    The general point is that the prometheus receiver inherits Prometheus's entire discovery model, including the fact that discovery is a separate concern from scraping. In Compose you write targets by hand. In phase 5 you do not: kubernetes_sd_configs, or the Operator's Target Allocator watching ServiceMonitor CRDs, does the finding. Static targets are the thing that does not survive contact with an autoscaler, and noticing that here is cheaper than noticing it in a cluster.

  • 02

    The mongodb receiver is the officially blessed, semantic-convention-correct way to observe MongoDB, and this phase runs a third-party exporter alongside it that produces seventy times more series. Justify that, then say what it would take to drop the exporter.

    Answer

    The receiver reads serverStatus and dbStats. Neither contains replication lag, the oplog window, or election history — those come from replSetGetStatus and the local.oplog.rs collection, which the receiver does not read. A replica set with no lag metric and no oplog window is not observed; it is decorated. There is no configuration flag that adds them, because the metric set of a purpose-built receiver is a curated list and curation is a decision someone else already finished making.

    To drop the exporter you would have to get those metrics into the receiver — which means an upstream contribution to mongodbreceiver, not a config change. That is a real option and a reasonable one; it is also a different project. The interim answer is to run both and pay the cardinality, which is why filter/cardinality exists in the same config.

    The generalisation matters more than MongoDB: evaluate a receiver by what it cannot tell you, not by how clean its names are. Do it before you build dashboards on it.

  • 03

    You have a MongoDB latency spike at 14:02 and a slow trace in Tempo at 14:02. Grafana will not link them. Why not, and what is the strongest correlation you can actually build?

    Answer

    Because there is no trace_id anywhere in the MongoDB metric, and there never can be. The application's CLIENT span knows it called Mongo; Mongo does not know it was called by a trace. The trace_id-to-log link that works for order-api works because the Java agent put the id into the log record at the moment of writing. Nothing did that for a scraped counter, and nothing could — a metric is an aggregate over many requests by construction, so there is no single trace to point at.

    The strongest join available is resource attributes plus a time window: same service.instance.id (or k8s.pod.name in phase 5), same minute. That is enough to put the panels next to each other and let a human do the inference, which is what a good dashboard is for. It is not a click-through and pretending otherwise builds a false expectation.

    The exception worth knowing: exemplars. A histogram bucket can carry a trace ID for one sampled observation, which does give metric-to-trace click-through — but only for metrics your instrumented application emits, never for a scraped third-party endpoint.

  • 04

    filter/cardinality removes 63% of the series. Name the two cheaper controls used in this same config, explain why they are cheaper, and say what class of problem no filter can solve.

    Answer

    Not asking: prometheus.return_per_object_metrics = false, plus naming exactly three families on /metrics/detailed. Not scraping: MinIO's /minio/v2/metrics/bucket is never fetched at all.

    Both are cheaper because the data never crosses the network, never enters the Collector's memory, never passes through memory_limiter's accounting, and never gets batched and dropped. A filter processor pays the full cost of receiving and parsing every data point in order to throw it away. The ordering memory_limiter → enrichment → filtering → batch is designed around this: filtering happens as early as it usefully can, and the earliest possible place is outside the Collector.

    What no filter can solve is unbounded label values on a metric you want. order.id on orders_created_total cannot be filtered by name, because the name is fine; dropping the label collapses the series you meant to keep. That has to be fixed where the instrument is created.

  • 05

    Killing the Mongo primary produced five series from three members of mongodb_rs_members_state. Explain the mechanism, name a metric in your own application with the same shape, and give two defensible responses.

    Answer

    A Prometheus series is identified by its full label set, so a label whose value changes over the lifetime of the thing it describes does not update a series — it ends one and starts another. member_state=PRIMARY becoming member_state=(not reachable/healthy) is two series, not one changing value. rs_state on every mongodb_ss_* series has the same property, which is why a single failover forks thousands of them.

    The shape in your own code is any label carrying mutable state rather than identity: status on a long-lived gauge, version during a rolling deploy, leader=true|false, feature_flag_variant. The tell is: could this label's value change while the underlying entity stays the same? On a counter it is usually fine and often the point (status=ok|error partitions the count). On a gauge describing an entity it is a series fork.

    Two defensible responses: drop the label with a transform statement and keep the numeric value, which is where the information actually was; or keep it, and know that graphs will show a line ending and another beginning, and that rate() across the transition sees a reset. What is not defensible is discovering it during the incident.

  • 06

    Phase 4 swaps Tempo, Loki and Prometheus for Elasticsearch and Kibana, and claims that only the exporters and service.pipelines blocks change. Given everything in this phase, is that claim true? Be specific about what survives and what does not.

    Answer

    The claim is true about the Collector, and this phase is the strongest evidence for it. All five receivers, both transform processors, filter/cardinality and resourcedetection are downstream-agnostic: they operate on OTLP, which is the internal representation regardless of where it goes. Nothing about scraping RabbitMQ or tailing mongod.log knows or cares that Loki is on the other end. Swap three exporter blocks and the pipe is repointed.

    What does not survive is everything above the seam. The three dashboards in grafana/dashboards/ are PromQL, and PromQL does not exist in Elasticsearch. The derivedFields trace link and tracesToLogsV2 are Grafana datasource configuration and have Kibana equivalents that must be built by hand. Every query in this explainer is rewritten.

    So the honest version of the claim is: the pipeline is portable and the interface is not. That is a real and valuable property — it means the expensive, subtle work of this phase (getting service.name consistent, choosing what to drop, parsing logs correctly) is not thrown away by a backend change. But "a few lines of exporter config" describes the migration of the plumbing, not of the observability practice built on top of it, and phase 4 should be read with that distinction in hand.

Next

Phase 4 keeps every receiver and every processor in this file and changes only the exporters, pointing the same telemetry at Elasticsearch with mapping.mode: otel. Then, for one session, at both backends at once — identical data in two stores, side by side — and the comparison gets filled in with measurements rather than opinions: index size for the same ingest, steady-state RSS, and how long it takes to write the same three questions in PromQL/LogQL/TraceQL and in ES|QL.
