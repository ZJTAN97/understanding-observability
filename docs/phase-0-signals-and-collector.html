Signals and the Collector

Before any MongoDB, RabbitMQ or MinIO: what OpenTelemetry actually is, what it deliberately is not, and the four moving parts of a Collector config you will read a hundred more times.

01

Where OpenTelemetry stops

OpenTelemetry stores nothing and draws nothing. It is a way to produce telemetry and a pipe to move it. Everything below the pipe is a separate product decision.

02

Three signals, three questions

People say “the three pillars”. Better framing: three answers to three different questions, at three wildly different costs.

A fourth signal, profiles (continuous CPU/heap profiling), reached stable status in OTEL recently. Ignore it until Phase 6 — it answers “which line of code burned the CPU”, one level below traces.

03

What is actually on the wire

OTLP is not a flat list of events. It is three nested levels, and the outermost one — resource — is the level most people ignore and later regret.

the same thing as JSON, over OTLP/HTTP

{
  "resourceSpans": [{
    "resource": { "attributes": [
      { "key": "service.name", "value": { "stringValue": "order-api" } }
    ]},
    "scopeSpans": [{
      "scope": { "name": "manual-curl" },
      "spans": [{
        "traceId":  "5b8efff798038103d269b633813fc60c",  // 16 bytes, hex
        "spanId":   "eee19b7ec3c1b174",                  //  8 bytes, hex
        "name":     "POST /orders",
        "kind":     2,                                 // 2 = SERVER
        "startTimeUnixNano": "1757000000000000000",
        "endTimeUnixNano":   "1757000000118000000"
      }]
    }]
  }]
}

Note what is not there: no duration field (it is end − start), no service name on the span (it lives on the resource), no parent pointer for a root span. Nanosecond Unix timestamps as strings, because JSON cannot hold a 64-bit integer.

04

Semantic conventions are the join key

A dashboard that shows metrics, logs and traces for “the order service” only works if all three agree on what that service is called. That agreement is the spec called semantic conventions.

Conventions exist for HTTP (http.request.method, http.response.status_code), messaging (messaging.system=rabbitmq, messaging.destination.name), databases (db.system=mongodb, db.collection.name) and more. Auto-instrumentation emits them for you; the job is mostly not breaking them with custom attributes.

Watch out

Semantic conventions are still churning. HTTP attributes were renamed (http.method → http.request.method) and many libraries straddle both. When a dashboard shows no data, a renamed attribute is the first thing to check.

05

Cardinality, the thing that kills clusters

A metric is not one number. It is one number per unique combination of its labels. That multiplication is how a 2 GB Prometheus becomes a 200 GB Prometheus overnight.

This matters for our stack immediately: MongoDB exposes per-collection and per-index metrics, and MinIO exposes per-bucket metrics. Both scale with how many collections and buckets you create. Part of Phase 3 is using the Collector's filter and transform processors to drop the ones you do not need — at the pipe, before storage.

06

The Collector is four words

Every Collector config you will ever read is receivers, processors, exporters, and a service block that wires them into pipelines. Defining a component does nothing until a pipeline references it — the single most common beginner bug.

phase-0/otel-collector-config.yaml

receivers:                      # how data gets IN
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }
      http: { endpoint: 0.0.0.0:4318 }

processors:                     # what happens on the way through
  memory_limiter:
    check_interval: 1s
    limit_percentage: 75       # shed load before the OOM killer does
  batch:
    timeout: 1s

exporters:                      # where data goes OUT
  debug:
    verbosity: detailed          # prints to the container's stdout

extensions:                     # not in a pipeline; cross-cutting
  health_check: { endpoint: 0.0.0.0:13133 }

service:                        # ← nothing above is active until named here
  extensions: [health_check]
  pipelines:
    traces:
      receivers:  [otlp]
      processors: [memory_limiter, batch]
      exporters:  [debug]
    metrics:
      receivers:  [otlp]
      processors: [memory_limiter, batch]
      exporters:  [debug]
    logs:
      receivers:  [otlp]
      processors: [memory_limiter, batch]
      exporters:  [debug]
  telemetry:
    logs: { level: info }

Two distributions, pick the right one

ImageContainsUse when
otel/opentelemetry-collectorCore only — otlp, batch, debugAlmost never
otel/opentelemetry-collector-contribEverything — prometheus, filelog, mongodb, rabbitmq, k8sattributes…Always, for this project

Every receiver we need for MongoDB, RabbitMQ and MinIO lives only in contrib. Reaching for the core image and wondering why filelog is an unknown type is a rite of passage; skip it.

07

Your three systems do not speak OTLP

This is the fact that shapes the rest of the project. MongoDB, RabbitMQ and MinIO have no OpenTelemetry inside them. The Collector's job is to go and fetch from them, in their own native formats, and translate.

08

Do it: a trace with no SDK

The fastest way to stop finding OTLP mysterious is to send some by hand. No app, no library — curl and a JSON body.

1

Start the Collector

cd phase-0
docker compose up -d
curl -s localhost:13133

You want {"status":"Server available", …}. That is the health_check extension, not a pipeline — extensions run outside the receiver/processor/exporter model.

docker compose logs -f

Send one trace, one log and one metric — all sharing a trace id

./send-telemetry.sh

5

Break it on purpose

Three deliberate failures. Do all three — each one saves you a future half-hour.

ChangePredict, then check
Remove debug from service.pipelines.traces.exporters, restart, resendTraces vanish; logs and metrics still print. The exporter is still defined — it is just unreferenced, so it does nothing.
Remove the whole traces: pipeline blockCollector still starts happily. POST /v1/traces now returns 404 — the receiver only serves signals some pipeline asked for.
Rename batch to batchh under processors:Startup fails hard: unknown type: "batchh". Config errors are fatal, never warnings.

Answer these before Phase 1

  • 01Which two layers of the stack does OpenTelemetry deliberately not provide, and why does that make backends swappable?
  • 02A dashboard needs “p99 latency of the checkout endpoint over 30 days”. Which signal — and why not the other two?
  • 03Where does service.name live: on the span, the scope, or the resource? What breaks if two services share one?
  • 04Why is user_id fine as a span attribute but not as a metric label?
  • 05You added an exporter and no data reaches it. What is the first line of config to check?
  • 06MongoDB is running. What must exist for traces of Mongo queries to appear — and why is the answer not “a Collector receiver”?
