The agent is a wrapper, not a watcher

This is the one idea everything else follows from. Get it and the rest is obvious.

The OpenTelemetry Java agent does not sit above your program watching for bad things. It cannot see your variables, your if statements, or your intentions. What it does is far dumber and far more mechanical: as your program loads, the agent rewraps methods that belong to libraries it recognises.

Spring AMQP is one of those libraries. So when a message arrives, the agent wraps the call to your @RabbitListener method in something roughly like this:

what the agent effectively wraps around your listener

// This is the agent's code, not yours. You never see it.
span = startSpan("orders.created process");
try {
    onOrder(order);              // ← your method runs here
    // returned normally? then nothing marks the span as failed
} catch (Throwable t) {
    span.recordException(t);     // ← the ONLY place an error gets recorded
    span.setStatus(ERROR);
    throw t;
} finally {
    span.end();
}

Read that catch carefully. It is the only route by which a failure becomes an error span. The agent learns that something went wrong in exactly one way: your method throws at it.

Now look at where our exception actually lives.

The mental model to keep

Auto-instrumentation watches the seams between your code and libraries. It has no visibility inside a single one of your methods. A try/catch that starts and ends in your own code never touches a seam — so from the outside, it never happened.

The failure was recorded — just not anywhere you looked

This is why it feels like a Tempo bug. The failure genuinely was captured. Two of the three signals caught it perfectly. The third, the one you searched, is the one that missed.

Notice the pattern. The two signals that worked are the two where you explicitly wrote something: log.error(...) and the status label on the histogram. The signal that failed is the one you assumed was automatic.

Two lines, and the span starts telling the truth

Since the agent cannot see into your catch block, you walk over and tell it. Span.current() hands you the span the agent has open right now — the one wrapped around your listener — and you write onto it directly.

OrderListener.java — the catch block, after

} catch (Exception e) {
    status = "error";

    // The agent is holding a span open around this call. Grab it.
    Span span = Span.current();
    span.recordException(e);                          // type + message + stacktrace
    span.setStatus(StatusCode.ERROR, e.getMessage()); // what {status=error} matches

    log.error("order processing failed order.id={}", order.id(), e);
}

recordException attaches the exception type, message and stack trace to the span as an event — a timestamped note hanging off it. setStatus flips the span's own verdict from UNSET to ERROR, and that verdict is the exact field a {status=error} search reads.

Leave the neighbours alone

Only the listener span goes red. The Mongo insert and the MinIO write stay UNSET — and that is correct, not an oversight. Those calls genuinely succeeded. Marking them failed would send the next person debugging this straight into the database, which is the one place the problem is not.

A span's status answers “did this particular operation fail?”, not “was this request part of something that went wrong?”.

One more thing you get for free. The service graph pairs spans into edges and counts the failed ones, so it starts reporting a failing edge on its own:

“Why not just let it throw?”

The obvious instinct, and a genuine trap. Worth understanding before you reach for it.

If you delete the catch and let the exception escape onOrder(), the agent's wrapper catches it and marks the span ERROR by itself. No OpenTelemetry code needed. So far so good.

But a thrown exception means something else to RabbitMQ. Spring AMQP takes it as “this message was not processed” and, by default, hands it back to the broker to try again. The same message. Immediately. Forever.

Where else this bites

This is not a RabbitMQ quirk, a Spring quirk, or a Java quirk. It is how every auto-instrumentation agent in every language works. Anywhere your code handles a failure gracefully, it also hides that failure from your traces.

  • ✕

    A @RestController that returns a 500 by hand

    Catching an exception and returning ResponseEntity.status(500) yourself. The framework never saw a throw, so the SERVER span is UNSET — though the http.response.status_code attribute will still give you away here.

  • ✕

    A retry that eventually gives up

    Three attempts inside one method, all caught, a default value returned. The span shows a slow success. Nobody ever learns the fallback fired.

  • ✕

    A circuit breaker returning a fallback

    Working exactly as designed, and completely invisible. This is the most dangerous one, because degradation is the entire point of the pattern.

  • ✕

    catch blocks that only log

    The single most common shape in any Java codebase. Every one of them is a hole in your traces.

The tell to watch for

Any time your logs and your traces disagree about how healthy a service is, trust the logs and go looking for a catch. Twenty-nine error lines against zero error spans is not a backend problem — it is a boundary problem, and the boundary is in your source code.

Remember this one sentence

An agent can only see exceptions that leave your method. A caught exception never leaves, so if you handle it, you have to report it.
